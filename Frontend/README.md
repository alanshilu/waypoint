# Waypoint frontend

Vite + React + TypeScript UI for the Waypoint road trip planner. It shows the two routes the backend generates for a trip (fastest and backroads), how they trade off, and the tool calls the agent makes to get there.

## Run it

```
cd Frontend
npm install
```

### Mock mode (default, no backend needed)

```
npm run dev
```

Open http://localhost:5173 and click the "San Francisco to Los Angeles" chip. Everything is served from `src/fixtures/` with simulated latency. The badge next to the logo reads "Mock data".

### Real mode (FastAPI backend)

1. Start the backend on port 8000 (it needs Postgres/PostGIS and the keys in `Backend/.env`):

   ```
   cd Backend
   python -m uvicorn app.main:app --port 8000
   ```

2. Start the frontend with the mock flag off:

   ```
   # PowerShell
   $env:VITE_USE_MOCK = "false"; npm run dev

   # bash
   VITE_USE_MOCK=false npm run dev
   ```

   Or copy `.env.example` to `.env.local` and set `VITE_USE_MOCK=false`. `VITE_API_BASE` changes the backend URL (default `http://localhost:8000`).

The backend only allows CORS from `http://localhost:5173`, so the dev server is pinned to that port.

Real mode writes to the database: each planned trip adds one trip row and two route rows, and uses the OpenRouteService quota.

## Scenic score

The scenic score is terrain only: climb density `d = (ascent + descent) / miles`, scored as `100 × d / (d + 40)` on a 0-100 scale (40 m/mi scores 50). Drive time is not part of it; the backend reports slowness separately as `duration_vs_fastest`. The formula and the reference constant are documented in `Backend/app/services/scoring_service.py`; `src/format.ts` and `scripts/make-fixture.mjs` repeat them and must be kept in step.

## Stops (points of interest)

Ask for "Stops near destination" or "Stops along the route" (the midpoint of the selected route, or of the fastest route if none is selected). The results are listed over the map and drawn as numbered markers; the map zooms to them, and the "Stops" button in the zoom toggle returns to that view. Mock results come from `src/fixtures/pois.json`.

## Checks

```
npm run typecheck   # tsc --noEmit
npm run build       # type-check, then production build into dist/
npm run fixture     # regenerate src/fixtures/trip.sf-la.json
```

## How real mode differs from mock mode

- **No agent endpoint.** The backend has no `POST /agent/message`. The UI tries it once, gets a 404, and falls back to a scripted runner in `src/agent.ts` that calls the same endpoints the agent's tools call, in the same order. The tool calls and latencies shown are real; the reply text is a template, not an LLM. The trace drawer says which source was used.
- **Elevation chart for new routes only.** The backend stores an elevation profile with each route it generates. Routes saved before that have none, so for those the panel is hidden and the map takes the full height.
- **No cache status.** The backend does not report cache hits, so the trace shows "cache not reported".

All translation between the backend's response shapes and the UI's types happens in `src/api.ts`.

## Layout

| Path | What it holds |
|---|---|
| `src/types.ts` | Shared types: the UI contract and the raw backend shapes |
| `src/api.ts` | One typed function per endpoint, the `USE_MOCK` switch, adapters |
| `src/agent.ts` | Agent turn runner (remote agent if present, scripted otherwise) |
| `src/state/TripProvider.tsx` | Context + reducer: trip, selected route, hover mile, chat |
| `src/components/` | RouteMap, RouteComparison, ElevationProfile, ChatPanel, TraceDrawer |
| `src/geo.ts` | Line simplification, mile markers along a route |
| `src/styles/tokens.css` | Design tokens (colours, fonts, layout sizes) |
| `src/fixtures/` | Mock data. `trip.sf-la.json` is generated by `scripts/make-fixture.mjs` |
